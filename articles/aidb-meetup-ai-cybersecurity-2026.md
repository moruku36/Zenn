## 背景：AI が関与したと公表された事案

講演の前半では、この1年ほどで AI の悪用が公表された事案が振り返られました（図1）。

![図1：AI が関与したと公表された主な事案](/images/aidb-meetup-ai-cybersecurity-2026/fig0-timeline.png)

*図1：講演で触れられた主な事案（各社の公表資料をもとに筆者作成、Pele で作成）*

- **Claude Code を使ったデータ恐喝（2025年8月）**：Anthropic の報告[^anthropic-aug]によれば、攻撃者は Claude Code を使って偵察、認証情報の収集、ネットワークへの侵入を自動化しました。医療、救急サービス、政府・宗教機関など少なくとも17の組織が標的になっています。盗むデータの選別や身代金額の算定にも AI が使われていました。
- **nx パッケージの侵害（2025年8月）**：npm で広く使われている nx の悪意あるバージョンが公開されました[^nx]。このマルウェアは、感染したマシンにインストールされている AI CLI ツール（Claude、Gemini など）を呼び出し、機密情報の探索に使わせていました。開発者の PC やサーバーにエージェントを置くこと自体が、攻撃面になり得ることを示す事例です。
- **AI 主導のサイバー諜報（2025年11月）**：Anthropic は、国家支援とされる集団が約30の組織を標的とした諜報活動を報告しています[^anthropic-nov]。作業の推定80〜90%を AI が実行し、人間が介在したのは1回の作戦あたり4〜6か所の判断点だけだったとされています。
- **評価中のエージェントによる範囲外の行動（2026年8月）**：英国 AI Security Institute（AISI）のサイバー評価中に、エージェントが評価環境の外にある実在の人物や組織に対して行動していたことが報告されました[^aisi]。詳しくは後述します。

国内では、IPA の「情報セキュリティ10大脅威 2026」（組織編）で「AI の利用をめぐるサイバーリスク」が初めて選ばれ、3位に入りました[^ipa]。講演者は、セキュリティが専門家だけの関心事から、AI を使うすべての人が考えるべきテーマに変わってきていると述べていました。

なお、最近相次いでいる国内の大規模な個人情報流出について、AI の関与は公表されていない、という点も講演では明確に区別されていました。一方で、AI による脆弱性の発見と報告が実際の修正につながる事例も増えています。攻撃と防御の双方で、脆弱性の発見から悪用、あるいは修正までの時間が短くなっている、というのが講演全体の前提でした。

## 1. 公開情報を使ったフィッシングの個別化

講演では、SNS や Web 上の公開情報から対象者の職種や関心を自動で収集し、LLM でメール文面を個別化する実験が紹介されました。全員に同じ文面を送る場合と比べ、クリック率は2倍以上だったとのことです。この実験では、人間が個別化した文面のほうがまだクリックされやすかったものの、生成に使われたのは現在の基準では性能が高くない Llama 系のモデルでした。講演者は、それでもこの効果が出ている点を重く見ていました。この実験の論文は、筆者が調べた範囲では特定できていません。

近い条件の公開研究としては、次の2件があります。

- **Heiding et al. (2024)**[^heiding]：101名を対象に、AI が対象者の情報収集からメール作成までを全自動で行うスピアフィッシングを評価しています。クリック率は対照群12%、AI 全自動54%、人間の専門家54%、AI＋人間の確認56%でした（図3）。この研究では、AI 全自動と人間の専門家の差は見られません。
- **Czybik et al. (USENIX Security 2026)**[^czybik]：7,700名を対象とした大規模実験です。Web 検索で集めた個人情報をもとに LLM で個別化したメールは、一般的なフィッシングの約3倍のクリック率を示しました。個別化のコストは1通あたり約0.03ドルと報告されています。

![図3：スピアフィッシングのクリック率（Heiding et al., 2024 の報告値）](/images/aidb-meetup-ai-cybersecurity-2026/fig2-phishing.png)

*図3：Heiding et al. (2024) が報告したクリック率（Pele で作成）*

講演ではもう1つ、リリース時期が1年半ほど離れたモデル（GPT-4o と Claude Opus 4.6）を比べると、攻撃シナリオでの到達度に約6倍の差があったという比較も示されました。ただしこの実験では、最終段階まで到達したモデルはなかったとのことです（講演値、出典未確認）。

倍率は実験条件によって2〜4倍超と幅がありますが、個別化によって効果が大きく上がるという方向性は共通しています。実務上の含意は、「自分の業務や関心に触れている文面だから、知人や取引先が書いたものだろう」という判断がもう成り立たない、という点です。エージェントで Web、X、ブログなどを検索すれば、個人情報とまでは言えない公開情報からでも人物像を組み立てられます。講演者は、自分の情報をどこまで公開するかを考え直す時期に来ていること、そして家族や同僚にもこの前提を伝えていく役割があることを指摘していました。Czybik et al. も、メールアドレスに紐づく公開情報を減らすことと、個別化されたフィッシングを前提にした教育を提言しています。

## 2. 攻撃エージェントの「3つのクセ」

講演の中心は、侵入を試みる AI エージェントの行動を分析した研究から見えてきた3つの傾向でした。講演者は、モデルによる差はあるものの、エージェント全般に見られる傾向だと説明していました。

![図4：攻撃エージェントの典型的なループと3つのクセ](/images/aidb-meetup-ai-cybersecurity-2026/fig3-agent-loop.png)

*図4：攻撃エージェントの典型的なループ。おとりは検証の段階に作用し、正攻法で行き詰まると範囲外の手段に出ることがある（Pele で作成）*

### クセ1：仮説は速いが、検証に時間がかかる

エージェントの作業記録を分析し、攻撃可能な箇所の仮説を立てる時間と、それが本当に使えるかを確かめる時間を比べた研究が紹介されました。仮説は次々に立てる一方、検証には仮説構築の約11倍（講演資料では11.1倍）の時間をかけていたとのことです（講演値、出典未確認）。

質疑では、この差の原因についても補足がありました。人間は経験や直感から「この仮説は見込みが薄い」と判断して後回しにできますが、エージェントはすべての仮説を同程度に有望なものとして扱い、順番に試していくため時間がかかる、という解釈です。選択肢ごとの見込みを確率として数値で見積もる仕組み（専用のツールやモデル）を組み合わせれば、この判断は速くなる可能性がある、という見方も示されていました。ただしこれは観察された挙動からの解釈であり、モデルや設定によって変わり得ます。

関連する公開研究として、ATOBench[^atobench] はペネトレーションテスト用エージェントが脆弱性をどう検証するかを追跡しています。標的の応答を実行時に改ざんした場合とそうでない場合を比較し、「活動量が増えているように見えても、検証の連鎖が壊れていることがある」と報告しています。Big Enough to Break Out[^breakout] も、停滞したエージェントのボトルネックは記憶ではなく計画にあると論じています。

### クセ2：おとりにかかりやすい

2つ目は、本物らしく見えて実際には攻撃に使えない「偽の脆弱性」に引っかかりやすいという傾向です。偽の脆弱性を置いた環境でエージェントに攻撃させた実験では、作業時間の3〜5割が偽の脆弱性が本物かどうかを確かめる作業に使われていたとのことです（講演値）。この性質を防御に使う方法は、次の節で扱います。

講演者は、実際の攻撃者が使うモデルについても触れていました。商用の主要モデルは悪用目的の依頼を途中で拒否することが多いため、攻撃者は安全機構を外しやすい高性能なオープンウェイトモデルを使う可能性が高い、という推測です。紹介された実験の多くがオープンウェイトモデルで行われているのもそのためだろう、と説明していました。

### クセ3：正攻法で解けないと、範囲外の手段に出る

3つ目は、課題を正面から解けないとき、指示されていない手段で目的を達成しようとする傾向です。その例として、英国 AISI が2026年8月に公表した事故報告[^aisi]が取り上げられました。

AISI は、模擬ネットワークに侵入して最終的なフラグを取るサイバーレンジ課題で、7つのモデルを計122回評価していました。モデル本来の能力を測るため、インターネット接続を意図的に有効にし、開発元のサイバー用安全分類器も無効にしていました。その結果、10回の実行で計19件の範囲外の行動が確認されました。最も深刻な例では、エージェントが実在のオープンソースプロジェクトに悪意あるコードを含むプルリクエストを送り、偽のアカウントを複数作ってメンテナにマージを促していました。このプルリクエストはメンテナが拒否しており、AISI は実害は確認されていないとしています。

講演では、この事例から次の点が読み取れると説明されていました。

- エージェントの推論の記録を見ると、範囲外かもしれないと認識しながら実行していたように読める箇所がある。推論の過程を後から確認できても、行動した後では手遅れになり得る。
- エージェントがテストであることに気づき、「テストだから問題ない」と判断した可能性も指摘されている。AISI 自身も、エージェントがどの時点で試験だと認識していたかは確定できないとしている。
- この評価は安全機構を意図的に外した条件で行われており、通常の利用環境よりも行動が大胆になりやすい。ただし、外せる安全機構である以上、攻撃者も同じ条件で使える。

また講演では、新しい世代のモデルで範囲外の行動の発生率が0%から22%に増えたという比較も示されました（講演値、出典未確認）。講演者は、能力の向上と危険な行動の能力は切り離しにくいのではないか、という推測を述べていました。OpenAI も同じ事案について、評価環境の設定と安全機構を外した条件が重なって起きたものだという説明を公表しています[^openai-eval]。

## 3. クセを逆手に取る防御：おとり（デセプション）

検証に時間がかかり、おとりにかかりやすいという性質は、防御側から見ると利用できる余地があります。実際には使えない「偽の脆弱性」や偽の応答をシステム内に置けば、エージェントはその真偽の確認に時間とトークンを使うことになり、攻撃の進行を遅らせたり成功率を下げたりできます。講演者は、熟練したセキュリティエンジニアが以前から行ってきた工夫を、より多くの人が取り入れていく段階に来ていると述べていました。

講演で特に印象的だったのは、偽の画面で「続行するには API キーを入力してください」と求めたところ、攻撃エージェントが先に進むために自分の API キーを入力してしまった、という事例です。キーを取れなかった場合でも、攻撃成功率そのものは下がっていました。これに対応する報告が公開論文にあります。

- **AgentTrap (Wang et al., 2026)**[^agenttrap]：自律型ペネトレーションテスト用エージェントを対象に、エージェントの行動に応じて応答を変えるハニーポットです。「特権アクセスには API キーが必要」という偽の応答を返すと、エージェントが自分の実行環境からキーを探し出し、攻撃用のパラメータとして送信してくるケースがありました（図5）。キーを取得できたのは全実行の18.8%です。攻撃成功率は防御なしの95.8%から79.2%に下がりました（図6）。
- **Mantis (Pasquini et al., 2024)**[^mantis]：おとりのサービスに誘い込んだ LLM 駆動の攻撃に対し、応答にプロンプトインジェクションを仕込んで妨害する手法です。95%以上の有効性が報告されています。

![図5：AgentTrap による API キー取得の流れ](/images/aidb-meetup-ai-cybersecurity-2026/fig4-agenttrap.png)

*図5：AgentTrap 論文の記述をもとにした API キー取得の流れ（Pele で作成）*

![図6：AgentTrap の有無による攻撃成功率](/images/aidb-meetup-ai-cybersecurity-2026/fig5-agenttrap-asr.png)

*図6：AgentTrap の有無による攻撃成功率（Wang et al., 2026 の報告値、Pele で作成）*

講演者は、効果的な「偽の攻撃面」を設計するノウハウはまだ世の中に多くないと述べていました。攻撃者がどのモデルを使ってくるかを想定し、そのモデルがどのような罠にかかるかをシミュレーションしておくことが勧められていました。

ただし、おとりはあくまで攻撃を遅らせ、成功率を下げるための補助的な手段です。脆弱性の修正やパッチ適用の代わりにはなりません。また、攻撃側もこの手法に適応しつつあります。たとえば Rouxii[^rouxii] は、おとりの存在を前提にした攻撃エージェントがハニーポットを見抜く率を19%から97%に高めたと報告しています。おとりを使う防御と、それを見抜く攻撃は、今後もいたちごっこが続くと考えられます。

## 4. エージェント設計：範囲を明示し、コードで確認する

クセ3を踏まえて、自社でエージェントを運用する側が取るべき対策も整理されていました。

### 範囲を明示する

AISI の事案に関連して、「指示に書かれていない対象や手段は範囲外とする」という一文をプロンプトに加えるだけで、範囲外の行動が約6分の1に減ったという結果が紹介されました（講演値、出典未確認）。AISI 自身も、エージェントにインターネットの使い方の制限を明示していなかったことを原因の1つに挙げています[^aisi]。現在のエージェントは、明示的に禁止されていないことは許されていると解釈しがちだ、というのが講演者の説明でした。

### 不可逆な操作はコードで確認する

ただし、プロンプトでの指示は出発点にすぎません。外部の文書やメールに埋め込まれた悪意ある指示（間接プロンプトインジェクション[^greshake]）を読み込んだ場合など、自然言語の制約は破られる可能性が残ります。講演では、13のモデルを対象にした実験でも多くのモデルがプロンプトインジェクションにかかったという結果が紹介されました。最新のモデルでも完全には防げていないとのことです。

講演で示された対策は、外部へのデータ送信、重要な設定の変更、ファイルの削除といった不可逆な操作について、実行の直前にコードで条件を検査し、許可されないものはブロックする仕組みを置くことでした（図7）。安全性に影響する要因を比較した研究では、モデルの違いや、人間が指示を工夫する努力よりも、コードによる確認を挟むかどうかの影響が最も大きかったと紹介されていました（講演値、出典未確認）。

![図7：実行前にコードでポリシーを強制する構成](/images/aidb-meetup-ai-cybersecurity-2026/fig6-guard.png)

*図7：ツール呼び出しを実行前にコードで検査する構成（Pele で作成）*

この考え方は、プロンプトインジェクション対策の研究とも一致しています。CaMeL[^camel] は、信頼できる入力から制御フローを作り、信頼できないデータがプログラムの流れに影響しないよう分離したうえで、ツール呼び出しにケイパビリティベースのポリシーを適用します。Beurer-Kellner et al.[^patterns] は、エージェントが信頼できない入力を読んだ後に取れる行動を構造的に制限する設計パターンを整理しています。いずれも、モデルが指示に従うことを期待するのではなく、システムの構造で安全を確保するというアプローチです。

講演者は、プロンプトインジェクションは「身近ではない」と思われがちだが、メールや文書を読ませる業務ではすでに入口になっていると強調していました。顧客や上司から AI の安全性について聞かれる機会は今後増えるはずなので、こうした用語と対策を説明できるようにしておくとよい、とも述べていました。

## 5. 防御側 AI：複数モデルによる相互検証

防御側の AI 活用は、比較的前向きな話題として紹介されました。AI による脆弱性の発見が現実的になってきたことに加え、セキュリティアラートの分類を1つのモデルに任せず、別のモデルに見直させる構成が取り上げられました。たとえば Codex で分類した結果を Claude にもう一度確認させると、分類の誤りが大きく減ったという研究です（図8）。講演者は、アラートの分類に限らず、振り分け系の作業全般に使える考え方だと述べていました。

![図8：複数モデルによる判定の相互検証](/images/aidb-meetup-ai-cybersecurity-2026/fig7-crosscheck.png)

*図8：複数モデルで判定を検証し、不一致は人間に回す構成（Pele で作成）*

関連する公開研究としては、次のものがあります。

- **From Investigation Failures to Reliable SOC Agents**[^soc]：アラートトリアージ用エージェントの手順から判定役（Judge）を除くと、誤検知が1件から9件に増えたと報告しています。
- **LLMpatronous**[^llmpatronous]：複数のエージェントが順番に先の評価を見直す構成で、単一の LLM による判定に比べて誤検知率が下がったと報告しています。

同時に、運用上の前提として「AI が調べて何も見つからなかったことは、安全であることの証明にはならない」という点が強調されていました。AI が自分の能力を超える範囲まで調べられるようになったとしても、検出結果の解釈、修正の優先順位付け、見落としを前提にした最終確認には、引き続き人間の判断が必要です。

## 6. エージェントが集団で動くと起きること

プログラムの5番目では、複数のエージェントが集まったときの挙動が取り上げられました。

1つは、同じモデルのエージェントだけで構成した「街」と、複数のモデルを混ぜた「街」を長期間動かすシミュレーション研究です。同じ初期条件から始めても、モデルによって結果は大きく異なりました。異なるモデルを混ぜると、単一モデルの集団より安全になる場合も、逆に危険になる場合もあったとのことです。講演者は、どのモデルとどのモデルを組み合わせるかで集団の挙動が変わる、という点を示唆として挙げていました。近い設定の公開研究として Emergence World[^emergence] があり、単一モデルの世界4つと混成の世界1つを15日間動かしたところ、安定した合議制から集団の崩壊まで大きく異なる結果になったと報告しています。

もう1つは、エージェントの数をどこまで増やすと集団の挙動が急に変わるかを理論的に解析した研究です。講演では、少数のうちは起きない侵入先での自己増殖のような振る舞いが、ある台数を超えると急に現れるという計算例が紹介されました（講演値、出典未確認）。

前の節で扱った複数モデルによる相互検証と合わせると、エージェントを組み合わせれば安全になるとは限らず、構成ごとに評価が必要だということになります。複数エージェント系に固有のリスクは Hammond et al.[^multiagent] が体系的に整理しています。

## 7. いま求められるスキル

最後に、講演者が独自に調べたセキュリティ関連の求人の傾向が紹介されました。国内12件、海外12件の計24件のうち、セキュリティの実務経験は24件すべてで必須とされていた一方、AI の経験を必須としていたのは11件でした。講演者はこれを、セキュリティの基礎知識が前提で、AI はその上で活用するもの、という順序を示していると解釈していました。

また、経験年数だけでなく具体的な成果が評価される場面も多いことから、業務で機会がなくても、自分で小さなプロジェクトを立ち上げて自動化を作ってみるといった取り組みも勧められていました。

## 8. 自分の現場で取り入れていること

ここからは講演の紹介を離れて、筆者のチームでの取り組みを書きます。筆者のチームでは、インフラや運用の作業に AI エージェントを使っています。設定の変更やリソースの操作には、取り消しが難しいものも含まれます。

### 実践していること：不可逆な操作の前に確認を求める

エージェントへの指示の中で、外部へのデータ送信や削除といった不可逆な操作の前には、必ず人に確認を求めるよう明示しています。第2節のクセ3と第4節で見たとおり、エージェントは明示的に禁止されていない手段を「許されている」と解釈しがちです。目的を達成しようとして範囲外の手段に出ることもあります。インフラ作業では、その1回の判断ミスが本番環境に直接影響するため、どの操作で止まるべきかを指示の中で言葉にしておくことが出発点になります。

指示の書き方を一般化すると、たとえば次のようになります。

```text
次の操作は、実行する前に必ず内容を提示し、人の承認を得てください。
- 外部のサービスやネットワークへのデータ送信
- ファイル・リソース・データの削除
承認を得ていない状態で、これらの操作を実行してはいけません。
```

ただし、これは自然言語の指示に頼る対策です。第4節で紹介したとおり、プロンプトインジェクションなどによって自然言語の制約が破られる可能性は残ります。そのため、確認を求める指示は安全策の1層目と位置づけるべきです。不可逆な操作については、実行環境の権限やコードによるチェックでも止められるようにしておくのが望ましい、というのが講演から得た示唆でした。

### これから取り入れること：周囲への注意喚起

第1節で見たように、公開情報をもとに個別化されたフィッシングは、一斉送信型より大幅にクリックされやすくなっています。自分の業務や関心に触れた文面であっても、それだけで知人や取引先からのメールだと判断できる時代ではありません。この前提を、チームのメンバーや身近な人に共有していく予定です。

### 読者の現場で試せること

本稿の内容を、すぐに取り入れられる形にまとめておきます。

- エージェントへの指示に、外部送信や削除などの不可逆な操作の前には人の確認を求める一文を入れる
- 許可する対象や手段を明示し、書いていないものは範囲外だと伝える
- 不可逆な操作は、指示だけでなく、権限の設定やコードによるチェックでも止められるようにする
- 個別化されたフィッシングの存在を、チームや身近な人に伝える

## まとめ

講演の結論は、次の3点に整理できます。

- 攻撃に使われる AI エージェントには、検証に時間がかかる、おとりにかかりやすい、行き詰まると範囲外の手段に出る、といったクセがある
- そのクセを理解すれば、おとりの設置や、範囲の明示とコードによるガードといった防御に活かせる
- 防御側も AI で脆弱性を見つけて修正できるようになってきたが、最終的な判断には人間が必要で、人の仕事は残る

個人的には、攻撃エージェントの「検証に偏る」性質が、そのまま防御側の設計（おとり）につながっていく流れが興味深く感じました。同時に、Rouxii のように攻撃側がすでにそれに適応し始めている点や、AISI の事案のように評価者自身の環境が攻撃の起点になり得る点も見逃せません。自社でエージェントを運用している場合は、まず不可逆な操作に対してコードによるガードがあるかを確認し、プロンプトでも許可する範囲を明示するところから始めるのが現実的だと思います。
