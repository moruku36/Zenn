## はじめに

クラウドエンジニアの仕事をAIへどこまで任せられるのか。自分の仕事を題材に、実際に試してみました。

今回は仕事を二つに分けています。

- Level 2：人間が構成と安全条件を決めた環境を、AIが実装・運用できるか
- Level 3：顧客要件から、採用判断に使えるクラウド設計をAIが作れるか

結果を先に書くと、Level 2ではAWS・Azure・Google Cloudの小規模な検証環境で、構築から障害試験、復旧、削除まで完了しました。一方、Level 3の最新試行D5は独立したAIレビューで77/100点。合格条件を満たさず、採用判断はHOLDでした。

この記事では、できたことに加えて、失敗したところと、人間の判断が必要だったところをまとめます。Level 2は実環境の実行記録、Level 3は設計文書の机上評価です。二つを同じ意味の「成功」として扱わないようにしています。

## 検証の範囲

Levelは今回の独自分類です。資格や業界標準に公式に対応するものではありません。単純な構築や知識確認を想定したLevel 1は今回は実施していません。

また、クラウドエンジニアという職業全体の代替率を測った実験でもありません。人間だけで同じ作業をした場合との時間・費用・品質比較や、統一条件でのモデル比較は行っていません。

参照した主な記録は次の二つです。

- [Level 2：3クラウドの実装・運用ライフサイクル検証][l2-report]
- [Level 3：要件からの設計に関する方法と結果][l3-methods]

## Level 2 人間が設計した環境をAIに実装してもらう

### 共通の構成と役割分担

対象は、L7ロードバランサーの配下にPrivate VMを2台置くWeb基盤です。VMに公開IPを付けず、インターネットから直接SSHできない構成にしました。

| 項目 | AWS | Azure | Google Cloud |
| --- | --- | --- | --- |
| 公開入口 | Regional ALB | Application Gateway | Global external Application Load Balancer |
| バックエンド | AZを分けたEC2 2台 | Zoneを分けたLinux VM 2台 | Regional MIGで管理するVM 2台 |
| 起動時などの外向き通信 | S3 Gateway Endpoint | NAT Gateway | Cloud RouterとCloud NAT |
| Remote State | S3 | Blob Storage | Cloud Storage |

同じ要件でも構成は完全には同じになりません。Google CloudではMIGを使い、AWSとAzureでは個別のVMを管理しています。Global LBを使ったことも、バックエンドを複数リージョンへ展開したことを意味しません。

人間は要件、変更してよい範囲、公開・権限の安全条件を決め、必要な変更や破棄を承認しました。AIにはTerraform実装、GitHub Actions、長期鍵を置かない短期認証、Remote State、監視、選定した障害試験、復旧、cleanupまでを任せています。

### 「作成できた」以外に何を確認したか

完了の判断には、以下の記録を使いました。

- 構築：applyの終了に加え、LB経由のHTTP 200とBackendの正常性
- CI/CD：短期認証、Remote Stateの初期化、planとapply
- 整合性：移行・修正・復旧後のNo changes
- 監視：選定した障害に対するアラート状態と復旧
- 削除：delete-only plan、Stateが空であること、対象リソースの残存確認

実行記録上、3クラウドでこのライフサイクルを完了しました。削除したTerraform管理項目は次のとおりです。

| クラウド | 環境本体 | State・認証などのBootstrap | 合計 |
| --- | ---: | ---: | ---: |
| AWS | 39 | 9 | 48 |
| Azure | 41 | 12 | 53 |
| Google Cloud | 25 | 13 | 38 |
| 合計 | 105 | 34 | 139 |

139件はTerraformが管理する項目の数です。VM台数や課金対象の数とは一致しません。「残存0」も、今回管理したactiveリソースを対象とした確認です。アカウント全体が空になったことや、後日請求が発生しないことまでは保証していません。

根拠：[Level 2最終レポートの評価方法・定量結果・cleanup][l2-report]。

### AWS パッケージを取得できずALBが502を返した

非公開EC2の外向き通信が不足し、Nginxの導入に失敗しました。AIは原因を調べ、S3 Prefix List宛てのHTTPS通信を限定的に追加して復旧しています。

Private VMを作るときには、受信経路に加えて、起動時に何をどこから取得するのかも確認する必要がありました。この構成のS3経由の取得は採用OSのパッケージ取得経路に依存するため、任意の外部リポジトリへの通信を許可した構成ではありません。

### Azure applyは成功したが12資源のタグが消えた

ローカルとCIでタグの入力が異なり、CI側のapplyが追加タグを削除しました。処理自体は正常終了していても、意図した変更にはなっていません。

入力を共通化し、人間の承認後にタグだけを修復しました。コマンドの終了コードに加えて、planの差分が意図と一致しているかを見る必要があります。

### Google Cloud 既存18資源が新規作成扱いになった

共有するStateの参照先を示すbackend宣言がGitで追跡されていませんでした。そのためCIは既存Stateを参照できず、18資源の新規作成を計画しました。

このplanはapply前に停止し、backend宣言を修復しています。AIに作業を任せるうえでは、想定外の作成・削除・置換を止める条件も必要でした。

以上の3件は[最終レポートの失敗・復旧記録][l2-report]にまとまっています。

### Level 2で確認できていないこと

監視では、設定と選定した障害に対する状態変化を確認しました。ただし、外部の通知先はいずれも未構成で、担当者への通知到達までは検証していません。クラウドごとに障害の与え方も異なるため、検知速度や可用性の優劣は比較できません。

AWS、Azure、Google Cloudの順に実施し、前の失敗から得た知見を次へ持ち込んでいます。人間の介入の集計単位も揃っていないため、介入削減率やクラウド別の成功率は算出していません。

さらに、実行記録があることと、公開コードをそのまま再実行できることは別です。最終レポートではバージョンやCIの統制に関する再利用時の確認事項も挙がっています。今回の記事作成でクラウドへ再接続したり、再実行したりはしていません。

この結果が示すのは、経験のあるエンジニアが設計・安全条件・承認を持った、小規模で破棄可能な環境での到達点です。本番の長期運用やSLOまで実証したとは扱っていません。

## Level 3 顧客要件から採用できる設計を作れるか

Level 3では、会員向けアプリの要件を渡し、AWS・Azure・Google Cloudの設計を求めました。主な条件は次のとおりです。

| 観点 | 条件 |
| --- | --- |
| 機能・規模 | 登録、ログイン、プロフィール変更、一覧・詳細、お気に入り、管理者更新。初期1万会員、月間100万PV |
| 性能 | 動的要求は通常10 req/s、ピーク100 req/sを15分、読書き9:1。静的要求は別。同時500人。主要APIのp95が500ms以内、サーバー側エラー率1%未満 |
| 可用性 | 計画停止と依存基盤の故障を含め、月間99.9% |
| 復旧 | サービス影響発生から、検知と復旧後5分の安定確認を含めたRTO 30分、RPO 5分 |
| データ | 本番データとバックアップを日本国内に保存。退会データは稼働系から30日以内に削除、バックアップ保持は最大35日、復元時は再削除 |
| 運用 | 開発5名、インフラ1名。平日日中対応で、夜間の即時対応は保証しない |
| 予算 | 本番と最小限の開発・試験環境で税込月10万円。必須の通信・監視・ログ・バックアップ等を含み、人件費等は別記 |

RTO/RPOはプロセス、実行環境、DB、単一AZの障害が対象で、地域全体の障害は対象外です。これらは設計検証の要件であり、実サービスで観測した性能ではありません。

予算内という判断は、無料枠、期間限定クレジット、長期契約割引に依存させない条件です。

条件の数字だけを並べると設計できそうにも見えます。しかし、平日日中対応で30分以内の復旧をどう成立させるか、必要な費用をすべて含めて予算に収まるかなど、具体化すると判断や根拠が必要になります。

根拠：[顧客回答][l3-answers]、[要件文書][l3-requirements]。

### 評価方法を自己採点から独立レビューへ変更した

9月の初期検証では、設計したAIによる自己採点でAが61→65点、Bが66点でした。10月の追加検証では、設計担当とは別のAIが文書を評価しました。D4とD5では設計と証拠を固定し、匿名化した資料をレビューしています。

合格条件は、以下をすべて満たすことです。

1. 加重総点が80/100以上
2. 全11評価項目が5段階評価で3以上
3. 必須6項目が4以上
4. 未解決のP0がない
5. 必須採用条件の6ゲートがすべてPASS

必須6項目は、要件、構成、セキュリティ・権限、可用性、費用、バックアップ・DRです。総点だけでは合否は決まりません。人間による採点や採用承認は得ておらず、独立AIレビューも机上評価の範囲です。

### 最新の結果はD5の77点でFAIL、採用HOLD

| 試行 | 指定した設計側の設定 | 独立評価の点数 |
| --- | --- | ---: |
| D1 | GPT-6 Luna / Low | 53 |
| D2 | GPT-6 Luna / Medium | 72 |
| D3 | GPT-6 Luna / High | 69 |
| D4 | GPT-6.1 Sol / Medium | 78 |
| D5 | GPT-6.1 Sol / High | 77 |

この表のモデル名と推論設定は依頼時の指定です。実際の実行モデル・適用された設定は、レビュー側も含めてUNKNOWNです。

D1〜D4は前のレビューや指示を引き継ぐ反復で、D5もD4を修正しています。設計、証拠、レビュー担当などが変わっているため、この表からモデル性能や推論設定の効果だけを取り出すことはできません。9月の自己採点も、この独立評価の系列には混ぜていません。

2026年10月2日のD5は77点で、数値上の合格条件を満たさず、採用判断もHOLDでした。最高点78と最新結果77は区別しています。

同日に別途追加された要件変更は未採点で、D5の入力には含まれていません。その変更後の要件に77点を流用することもできません。

根拠：[方法と結果][l3-methods]、[D5最終レポート][l3-d5]。

### 何が採用を止めたのか

**費用は3/5で、必須項目の下限4に届きませんでした。** 月10万円以内の成立性、必須費用を含めた余裕、独自制御の開発・訓練工数、より安価な代替案の根拠が不足していました。不明な価格をゼロに置かなかったことは評価されていますが、それだけで予算内の設計が成立したことにはなりません。

**削除のゲートG3はHOLDでした。** 削除開始のイベント、削除台帳と紐づく情報の保持期間、証拠を独立して保管する責任、外部サービスやデータ受領者のコピーに対する責任が未承認でした。

**運用のゲートG4もHOLDでした。** 主担当と代替担当、承認済みの工数、休暇・不在時の対応、無人復旧の権限が確定していませんでした。平日日中の体制で30分以内の復旧を支えるには、設計文書に加えて、誰が何を引き受けるかを決める必要があります。

D5ではSQLベースのAdmissionCoordinatorなどの独自制御も追加しました。しかし、主要なリクエスト経路に入る仕組みについて、負荷、競合、遅延、復旧順序の根拠が不足していました。ComplexityはD4の4から3へ下がり、総点が1点下がっています。この3点は一般項目の下限を満たしており、費用の必須下限未達とは別です。

未解決P0は、所有者の判断、情報源へのアクセス、実環境検証の前提に関するもので、机上設計のP0欠陥が見つかったという意味ではありません。詳細は[D5の判定][l3-d5]と[ゲート一覧][l3-gates]に残しています。

## 二つの検証から考えたこと

Level 2では、設計と安全条件が決まった仕事をAIへ広く委任できました。コード生成に加え、API制約や認証の不一致、部分applyなどを調べ、限定した差分で修復し、後片付けまで進められた点が重要です。

Level 3では設計文書の具体性は増しましたが、採用条件を満たすところには到達していません。未取得の価格、未承認の担当者や権限、実測していない性能や復旧時間は、文書の説明を詳しくするだけでは埋まりません。

実務でAIに任せる場合には、作業範囲と一緒に、次の確認項目を用意するのがよさそうです。

- 何を成功とするか：HTTP応答、Stateの整合性、復旧、削除まで確認条件を決める
- いつ止めるか：想定外の作成・削除・置換、権限拡大、予算超過を停止条件にする
- 何が未確認か：机上の説明、実行記録、実測、承認済みの判断を分ける
- 誰が引き受けるか：運用・復旧・削除の担当と権限を明確にする

これらは今回の結果からの実務的な考察です。人間だけの作業との優位性や、より強いモデルなら合格するという結論はまだ出せません。

## まとめ

今回確認できた範囲では、人間が設計・安全条件・承認を持つことで、AIに小規模なクラウド環境の実装・運用作業を広く任せられました。顧客要件から採用可能な設計を作る検証は、最新D5が77/100点、FAIL・HOLDという結果です。

次に検証するなら、実際のモデルと設定、入力、証拠、評価条件を揃えた比較が必要です。実環境での負荷・復旧・費用の確認も別途必要になります。これらは今後の検証候補で、この記事で実施済みとはしていません。

AIへ渡す仕事を増やすほど、エンジニア側では要件、停止条件、承認に必要な証拠を決める仕事が重要になると考えています。
