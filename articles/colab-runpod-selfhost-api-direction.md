## 要約

Colab で動かしていた Qwen の Gradio アプリを出発点に、RunPod の GPU を借りて、オープンウェイトモデルを Open WebUI につなぐ検証を 3 段階で行いました。

- **Phase 1（2026-10-09）**：小型の Qwen2.5-1.5B-Instruct で、Open WebUI から 1 回だけ回答を表示できました。
- **Phase 2（2026-10-15）**：Qwen3.8-27B（BF16）でも、Open WebUI から 1 回だけ回答が返りました。品質や速度のベンチマークは取っていません。
- **Phase 3（2026-10-15）**：GLM-5.3-Flash の GGUF を H200 SXM で起動しようとしました。コンテナイメージの取得は終わりましたが、モデルの重みをダウンロードしている途中で、私が止めました。**モデルの出力は 0 件で、A/B の評価もできていません。**

同じ日の最終振り返りで、RunPod での検証は終了しています。この最終振り返りには、通常のコード・文書・最終成果物のレビュー向けに、MiMo-V2.6-Pro の API を「運用候補」として検討する、という方針が書かれています。ただし**未検証**で、API のアカウント、キー、呼び出し、結果のどれも確認していません。

ここからは、公開リポジトリには書いていない、**いまの私自身の考え**です。試していくなかで、繰り返し使う用途は、コード・文章・成果物の最終レビューに絞られてきました。使う頻度と GPU の運用の手間を考えて、実用上の方向としては MiMo-V2.6-Pro の API を選びました。ただ、API を呼び出したことも、組み込んだことも、性能を測ったことも、ほかより安い・優れていると確かめたこともありません。また、セルフホストに取り組んだ時間が無駄だったとは思っていません。いまも技術的な学びとして役に立っています。

この記事では、構成、試した順序、実際に確認できた範囲、つまずきと切り分け、GPU の時間課金に表れない作業、API とセルフホストを分ける軸、セルフホストがなお有力な場面を整理します。

## この記事の読み方

本文では、記録にある計測値（実測）、表示単価から計算した金額（試算）、私が下した判断、一般的な推論を、そのつど書き分けています。

金額は、特に断りがなければ**試算**です。各回の計測区間（Deploy の直前から、Stop 後に $0/時の表示を確認するまで）に、当時の表示単価を掛けたもので、確定した請求額ではありません。この計測区間は、応答の遅延でも、GPU が実際に動いていた時間でもありません。Phase 1 の金額は最終試験だけの分で、先行試験は含みません。どの回も請求額との突き合わせが済んでいないので、合算した総額は出していません。

根拠は、公開リポジトリの docs へのリンクとして本文中に付けました。リンク先は `main` の内容です。

## 構成：何をどうつないだか

全体像は次のとおりです（Phase 1・2 の簡略図です。Phase 3 も Pod 側の形は同じで、推論サーバーが llama.cpp になるだけですが、モデルの応答までは進んでいません）。

```text
Open WebUI
   │  認証付き HTTPS（RunPod の HTTPS プロキシ経由）
   ▼
RunPod 上の GPU Pod
   └─ 推論サーバー（Phase 1・2：vLLM ／ Phase 3：llama.cpp server）
        └─ オープンウェイトモデル（Qwen → GLM-5.3-Flash の GGUF）
```

- **Phase 1**：前段に認証を先に通すガードを置き、外に許可する経路を `GET /v1/models` と `POST /v1/chat/completions` の 2 つに絞りました。vLLM はその内側（loopback）で待ち受けています（[Phase 1 記録](https://github.com/moruku36/open-llm-multimodal-lab/blob/main/docs/runpod-phase1-verification-2026-10-09.md)。この記録は日本語のみです）。
- **Phase 2**：vLLM の API キーは RunPod の Secret 参照で渡し、ローカルの Open WebUI から OpenAI 互換の接続でつなぎました。認証なしの `/v1/models` が 401 になることは、リクエストを送る前に確認しています（[Phase 2 記録](https://github.com/moruku36/open-llm-multimodal-lab/blob/main/docs/runpod-phase2-verification-2026-10-15.ja.md)）。
- **Phase 3**：digest で固定した llama.cpp の server イメージに、`-hf` の指定で GGUF の重みを取得させる構成でした（[Phase 3 試行記録](https://github.com/moruku36/open-llm-multimodal-lab/blob/main/docs/phase3-trial-2026-10-15.ja.md)）。

運用面では、Phase 2 と 3 で、始める前に**時間と金額の上限**を承認しておきました（Phase 2 は 45 分・$3、Phase 3 は 75 分・$7 と停止条件 6 つ）。Phase 2 では、画面側の準備を GPU の起動前に済ませ、Deploy、1 回の確認、Stop、課金速度が $0 になったことの確認、Terminate の順に進めました。Phase 3 は、上限の範囲内で Stop し、そのあと Terminate しています。

結果を保存してから Pod を止めるジョブ API と実行器も、Phase 3 向けに設計していましたが、実装はしていません（[README.ja.md](https://github.com/moruku36/open-llm-multimodal-lab/blob/main/README.ja.md)）。RunPod のライフサイクルを管理するコードは、別リポジトリの [qwen-runpod-operations](https://github.com/moruku36/qwen-runpod-operations) にあります（Phase 2 記録の記載によるもので、このリポジトリの中身はこの記事のために確認していません）。

## 試した順序

1. **Colab/Gradio の Qwen アプリ。** このリポジトリは Qwen の Gradio アプリから始まり、その後 RunPod でのオンデマンド推論を試しました（[README.ja.md](https://github.com/moruku36/open-llm-multimodal-lab/blob/main/README.ja.md)）。README には、チャット専用とマルチモーダルの 2 本の Colab ノートブックが載っています。アプリ自体は今も残してあります。ただ、既存のアプリ全体やマルチモーダルのワークフロー全体を、RunPod 上で動かして検証したわけではありません（[最終振り返り](https://github.com/moruku36/open-llm-multimodal-lab/blob/main/docs/runpod-retrospective-2026-10-15.ja.md)）。RunPod に移った理由は公開記録に書かれていないため、この記事でも触れません。
2. **Phase 1（2026-10-09）。** 小型モデルを使って、画面から GPU 上のモデルまでの経路をつなぐ、最小の接続試験です。
3. **Phase 2（2026-10-15、[PR #44](https://github.com/moruku36/open-llm-multimodal-lab/pull/44)）。** 同じ経路で、モデルを 27B 級に大きくした短い接続試験を 1 回行いました。
4. **Phase 3（2026-10-15、[PR #45](https://github.com/moruku36/open-llm-multimodal-lab/pull/45)）。** GLM 系の 3 モデルを同じ課題で比べる計画を立て、そのうち GPU なしでできる準備と、A の起動までを実施しました。A は公式モデルの GGUF、B は abliterated の派生 GGUF、C はセキュリティ向けの FP8 版です（C は Flash ではなく、フルの GLM-5.3 がベースです）。README では、過去の計画として扱われています。
5. **終了と方針（2026-10-15、[PR #46](https://github.com/moruku36/open-llm-multimodal-lab/pull/46)）。** 最終振り返りで RunPod での検証を終え、レビュー用途の運用候補として MiMo-V2.6-Pro API を検討する方針を記録しました。

## つまずきと切り分け

最終振り返りの整理にならうと、ここで挙げるのは**運用上の不具合**で、モデルの推論能力や回答能力とは別の話です。プラットフォームやセキュリティ上の制約を、モデルの能力不足と読み違えないように、と最終振り返りも注意しています。

### Stop したら GPU が戻ってこなかった（Phase 1 の先行試験）

先行試験では、モデルの準備が終わるところまでは進みましたが、Open WebUI での回答は確認できないままでした。そのうえ Stop したあと、同じ Pod に GPU を割り当て直せませんでした。記録によると、RunPod は Stop した時点で GPU を手放すため、元のホストで別の利用者が GPU を使っていると、再開できません。container disk も Stop で消えます。そこで最終試験では、画面側の準備を先に済ませておき、新しい Pod が起動してから、接続先だけを更新する形に変えました（[Phase 1 記録](https://github.com/moruku36/open-llm-multimodal-lab/blob/main/docs/runpod-phase1-verification-2026-10-09.md)）。

### 引用符が消えて再起動を繰り返した（Phase 2）

JSON の値を取る起動引数を start command に書いたところ、RunPod が引用符を取り除いて渡し、vLLM が引数エラーで終了しては再起動する状態になりました。重みの取得前だったので、失ったのは時間だけです。引数を外して Pod を編集し、直しました。`/health` が 404 や 502 を返すだけでは、再起動を繰り返しているのか、読み込みが遅いだけなのか区別できません。そこで、起動直後の最初の 1 分で System／Container のログを見る、という手順を記録に加えました（[Phase 2 記録](https://github.com/moruku36/open-llm-multimodal-lab/blob/main/docs/runpod-phase2-verification-2026-10-15.ja.md)）。

### 最初のリクエストが拒否された（Phase 1・2）

Phase 2 では、Open WebUI 0.12.2 の Function Calling が既定で Native になっていました。そのせいで、有効なツールが `tool_choice: "auto"` つきで送られ、サーバー側に tool 関連の設定がない vLLM が拒否しました。チャットの Function Calling を Legacy に切り替えて再生成すると、回答が返りました。Phase 1 でも同じ操作で通りましたが、Phase 1 では、拒否の原因を実際に送った内容から確かめてはいません。

### 思考モデルと短い max_tokens（Phase 2）

Qwen3.8 は最初に思考を始めるので、max_tokens が 64 だと、本文が出る前に打ち切られることがあります。Open WebUI のカスタムパラメータで `chat_template_kwargs = {"enable_thinking": false}` を送ると、本文だけが返るようになりました。

### テンプレートの既定値（Phase 2）

RunPod の「vLLM Latest」テンプレートは、API キーの既定値が推測されやすい形になっていて、`HF_HOME` の既定も、永続 volume があることを前提にしていました。前者は Secret 参照に、後者は container disk 側に変えています。

### 取得中ずっと `/health` が 502（Phase 3）

Phase 3 では、`/health` がずっと 502 のままでした。llama-server は、`-hf` による取得が終わるまで待ち受けを始めないためで、サーバーのエラーや再起動のループは起きていません。進み具合は container disk の使用量で追いかけました。記録にある推移は次のとおりです。

| 時刻（JST） | container disk の使用量 |
| --- | --- |
| 23:13 | 約 16 GB |
| 23:15 | 約 35 GB（約 9 GB/分） |
| 23:18 | 約 51 GB（約 5.5 GB/分） |
| 23:29 | 約 69 GB（約 1.6 GB/分） |

Deploy 直前の計測開始は 23:08:35.5、イメージの取得とコンテナの作成が終わったのは 23:10:45 です。**イメージの取得は終わっていて、止めたのは重みを取得している最中でした。**事前に承認していた停止条件 3（モデルの起動から 25 分以内に準備完了）を満たせない見込みになり（中止時点の見込みでは、取得完了が 23:54 頃、準備完了が 23:58 頃）、23:31:12 に私が中止を指示して Stop し、そのあと Terminate しました（[Phase 3 試行記録](https://github.com/moruku36/open-llm-multimodal-lab/blob/main/docs/phase3-trial-2026-10-15.ja.md)）。取得速度が落ちた原因は、記録では特定できていないので、この記事でも推測は書きません。

最終振り返りは、Phase 3 について、イメージのダウンロードの失敗ではなく、モデルが劣っている証拠でも、RunPod が一般に使えない証拠でもない、と整理しています。Phase 1 と 2 は、それぞれ 1 回答まで RunPod 上でたどり着けました。

### GPU の供給（Phase 3）

Phase 3 では、当初予定していた H200 NVL が、承認の直後に在庫切れになりました。H200 SXM（単価は約 1.4 倍）に切り替えるために、上限を承認し直しています。GPU の供給も、結果を左右する変動要因として記録に残っています。

## GPU の時間課金に表れない作業

GPU の時間課金は目に見える数字ですが、検証にはそれ以外の作業もありました。公開記録から拾えるのは次のとおりです。

- **GPU を使わない準備。** Phase 3 の P3-0 では、次のことを GPU なしで済ませました。モデル台帳の作成と revision の固定（Hugging Face の公開 API を使い、ダウンロードはなし）、GGUF の先頭 8 MB のヘッダーの確認、推論イメージに対象モデルの実装が入っていることの確認、評価セットの整備、採点器を模擬サーバーで検証すること。採点器の初版は HTTP エラーを「拒否」と数えていたため、検証の途中で直しました。
- **起動前の画面設定。** Function Calling、max_tokens、思考のオフ、Model ID などを GPU の起動前に済ませたので、GPU を動かす時間を最小限にできた、と Phase 2 の記録にあります。
- **トラブルシュート。** Phase 2 の 875.1 秒のうち、引数エラーの修正に約 4 分（約 $0.12）かかりました。計測区間には、こうした作業の時間も含まれています。
- **停止の確認。** Stop 後に $0/時の表示になったか、Terminate 後に支出速度が $0 か、Pod が 0 台か、外からエンドポイントに届かない（404）か、を確認しました（どの項目を確認したかは回によって違い、上の「実際に確認できた範囲」の出典に書かれています）。
- **請求額との突き合わせ。** Phase 3 では、残高表示の減少が $3.17 だったのに対し、計算上の試算は約 $2.04 で、約 $1.1 の差がありました。請求の反映が遅れているだけかもしれませんが、確認できていません。最終的な請求額は照合しておらず、報告書に書いた範囲を超えるストレージや volume の削除も、未確認のままです（[最終振り返り](https://github.com/moruku36/open-llm-multimodal-lab/blob/main/docs/runpod-retrospective-2026-10-15.ja.md)）。
- **周辺の課題。** 環境や依存関係の互換性、認証の設定、引用符と引数の扱い、Open WebUI の設定、GPU の供給、大容量の重みの転送と保存、停止と請求の確認が必要だった、と最終振り返りにあります。

最終振り返りには「約 2 週間」という記述もあります。これは私が体感した、暦の上での準備の負担です。**実測した経過時間でも、GPU の稼働時間でも、ベンチマークの時間でもない**、と明記されています。この記事でも、これ以上は分解しません。上に挙げた項目のうち、時間が記録されているのは、Phase 2 の引数エラーの約 4 分と、各回の計測区間だけです。それ以外の準備や確認に何時間かかったかは、公開記録に残っていません。

## API かセルフホストか：判断の軸

ここは、次の 3 つの層に分けて読んでください。

- **公開記録（PR #46 の最終振り返り）：** 通常のコード・文書・最終成果物のレビューを想定して、MiMo-V2.6-Pro API（`mimo-v2.6-pro`）を運用候補として検討する、という**未検証の方針**です。API のアカウント、キー、呼び出し、結果は確認しておらず、組み込みもしていません。同じ作業で API とセルフホストを実測して比べた結果もありません（[最終振り返り](https://github.com/moruku36/open-llm-multimodal-lab/blob/main/docs/runpod-retrospective-2026-10-15.ja.md)）。この位置づけは、記録した当時のままです。
- **私のいまの考え（公開記録にはない）：** 繰り返し使う用途がコード・文章・成果物の最終レビューに絞られ、使う頻度と GPU の運用の手間を考えて、実用上の方向として API を選びました。これは私の判断で、測定の結果ではありません。
- **測定結果：** API については、ありません。呼び出しも、組み込みも、ベンチマークも、費用や品質の比較もしていません。最安だとも最良だとも言いませんし、順位をつける話でもありません。

なお最終振り返りには、このモデルは公式にオープンウェイトが公開されていて、API 専用ではない、とも書かれています。

以下は、判断に使える軸です。どれも一般的な推論で、私の環境で測った結果ではありません。MiMo の現在の料金や、提供元のプライバシーポリシーの個別の条項は、この記事を書いた時点で公式ページを確認していないため、取り上げていません。

1. **費用の比べ方。** 費用は、想定する使用量とあわせて比べるものです。Pod は時間（ドル/時）、API はトークン（ドル/トークン）で課金されるので、単価をそのまま比べることはできません。私が測った Phase 1〜3 の金額は、接続試験の計測区間のものなので、トークンあたりの費用には換算できません。API の料金は、使う時点で提供元の公式ページを確認してください。
2. **データの扱い。** コードや文書を外部の API に送ってよいかは、送る前に確かめるべきことです。提供元の公式ページで、データの保持や利用の条件、適用される契約、権限、リージョンを確認してください。私自身は、この記事を書いた時点でそれらを確認していません。API だから必ずプライベートというわけでも、セルフホストだから必ず安全というわけでもありません。
3. **使う量と継続性。** Pod は確保している時間に応じて、API は使ったトークンに応じて、費用が増えます。どちらが安いかは使う量しだいで、私は測っていません。（一般的な推論）
4. **運用に割ける時間。** 上の「GPU の時間課金に表れない作業」は、セルフホストなら自分で引き受ける作業です。希望どおりに GPU を確保できなかった場面があったことも、記録に残っています。（一般的な推論）
5. **変化への備え。** API は、料金や仕様が提供元の都合で変わることがあります。セルフホストは、モデルや推論基盤の更新を自分で追うことになります。（一般的な推論）

## セルフホストがなお有力な場面

最終振り返りは、セルフホストが向く場合として、再現性の固定、重みの管理、独自の要件、プライバシー設計、継続的に高い稼働率、を挙げています。ただし、データの扱いの確認と、実際の作業での費用比較は欠かせません。ここに私の推論を足すと、次のようになります。

- **特定の重みや量子化を固定したいとき。** Phase 3 の A と B は、量子化も容量も同じで、重みだけが違うので、公平に比べられると記録されています（[Phase 3 試行記録](https://github.com/moruku36/open-llm-multimodal-lab/blob/main/docs/phase3-trial-2026-10-15.ja.md)）。量子化と容量を固定して重みだけを変える比較は、1 つの提供元の API だけでは組みにくい種類のものです。（一般的な推論）
- **データを外に出せないとき。** 外部サービスに送れない入力があるなら、セルフホストは有力な候補です。ただし、自分の環境でデータがどう扱われるかも、確認する必要があります。
- **推論環境そのものを調整したいとき。** サーバーの設定や起動引数まで触る必要があるなら、セルフホストの領分です。
- **使用量が継続的に多いとき。** 運用の負担を引き受けられるだけの稼働率があれば、費用の見え方が変わるかもしれません。実測での比較は別途必要です。

RunPod 自体は、Phase 1 と 2 で 1 回答まで動きました。Phase 3 を中止したことは、RunPod が使えないことを示すものではありません。

## 学び（記録に残した教訓）

最終振り返りと各試行記録にある教訓のうち、この記事の流れに関わるものを挙げます。どれも**教訓として残しているだけで、予定している作業ではありません**。

- **起動引数は、事前にローカルでどう分割されるかを確かめる。** JSON の値を取る引数は start command に書かず、環境変数か設定ファイルで渡す。
- **起動直後のログは、最初の 1 分で見る。** `/health` の 404/502 だけでは、再起動の繰り返しと読み込み中を区別できない。
- **画面側の設定は、GPU の起動前に終わらせる。**
- **大きな重みの取得経路が最大のリスク。** GPU の料金を払いながら 100 GB 級の重みを `-hf` で取得するのは効率が悪く、速度も安定しなかった。同じリージョンのネットワーク volume に、安い CPU Pod などで先に取得しておく。並列ダウンロードと SHA-256 の照合を使う。GPU と volume のリージョンをそろえる。こうした案が記録されている。
- **停止条件は、取得と読み込みに分ける。** 今回の停止条件 3 は起動の失敗を想定して作ったが、実際には取得の速度で発動した。
- **代わりの GPU と上限も、最初から 2 段で承認しておく。** 在庫が変わっても、止まらずに済む。
- **停止した証拠をそろえる。** Stop 後に支出速度が $0 になる、Terminate 後に Pod が 0 台になる、外からエンドポイントに届かない、までを 1 回分の完了条件にする。
- **秘密情報の扱い。** API キーは Secret 参照で渡す。テンプレートの既定のキーは必ず上書きする。キー、接続先の URL、Pod の ID は、公開する文書に残さない。
- **運用上の不具合と、モデルの能力は分けて書く。** 設定や供給の問題を、モデルの推論能力の評価として読まない。
