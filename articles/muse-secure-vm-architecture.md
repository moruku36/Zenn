AIエージェントにメールやカレンダー、買い物を任せようとすると、すぐに一つの問題にぶつかります。**エージェントが仕事をするには資格情報が要るのに、資格情報を持たせたエージェントがだまされると、その資格情報ごと持っていかれる**、という問題です。

セキュリティ研究者の Simon Willison は、この条件がそろった状態を "lethal trifecta"（致命的な三要素）と呼んでいます。

- 個人データへのアクセスがある
- 信頼できないコンテンツ（Webページ、メール、ファイル）に触れる
- 外部へ通信できる

Meta が 2026年9月8日に米国で公開した個人向けAIエージェント **Muse** は、この三要素を全部満たす製品です[^meta-news]。利用者に代わってブラウザーを操作し、メールを読み書きし、買い物までします。それだけに、公開と同日に出された安全設計の技術ブログ[^meta-blog]は、モデルの性能ではなく「モデルがだまされても壊れない境界を、モデルの外にどう作るか」にほぼ全編を割いています。

本稿では、Meta の公開資料と、その解説・検証記事をもとに、Muse の技術スタックをインフラ、アプリケーション、AI構成、秘密の扱いの4層で整理します。

- インフラ：利用者ごとに1台の Linux VM（Muse Secure VM）を割り当て、中を2つのセキュリティドメインに分ける
- アプリケーション：エージェント本体とツールは「実行セル」に閉じ込め、コネクタの実処理はセルの外の特権分離ワーカーが行う
- AI構成：Muse Spark を中核に、文脈の組み立てとツール実行を繰り返すエージェントループと、ファイルとしての記憶
- 秘密の扱い：エージェントには権限のない代理トークンしか渡さず、本物の資格情報が使われるのは、送信の直前になってから

:::message
本稿は公開資料に基づく調査です。筆者は Muse の利用者ですが、Meta の内部実装そのものを確認したわけではありません。Meta が内部を見せていない部分については、その旨を明記しています。
:::

## 1. インフラ：利用者ごとに1台の Linux VM、中は2つのドメイン

### Secure VM

Muse は、利用者ごとに専用のクラウド VM を割り当てます。Meta の説明では、ブラウザー、CPU、メモリー、ストレージを持つ隔離された Linux コンピューターで、エージェントの活動の "system of record"（記録の正本）だとされています[^explainx]。

本稿の執筆セッションで割り当てられていた VM を測ると、次の値でした（観測）。

| 項目 | 観測値（2026-10-23） |
|---|---|
| OS | Linux x86_64（カーネル 7.0 系） |
| CPU | 2コア（ホストは AMD EPYC 9D25） |
| メモリー | 約 7.7 GiB |
| ホーム用ディスク | 100 GB |
| スワップ | なし |

繰り返しますが、これは一例です。この値から「無料プランはこのスペック」とは言えません。言えるのは、少なくともこのセッションでは、シェルスクリプトの実行や小さなビルドには困らない程度の、作業用 Linux マシンとして使える環境だった、ということまでです。

### 実行セルとホスト側ドメイン

VM の中身が、すべて同じように信頼されているわけではありません。公開資料によれば、中は信頼レベルの違う2つの領域に分かれています[^qiita][^forkast]。

**実行セル（runtime cell）** は、エージェント本体とブラウザー、ツールが動く場所で、systemd-nspawn のコンテナとして実装されています。

- セル内の root は、ホスト側では非特権ユーザーに対応づけられる。セル内で root 権限を奪われても、ホスト側では一般ユーザーのまま
- 独自のルートファイルシステムを持ち、ホスト側とは分離される
- システムコールがフィルタされ、`io_uring` など危険なものは塞がれる
- `CAP_SYS_PTRACE`（他プロセスの検査）や `CAP_NET_ADMIN`（ネットワークの再構成）といったケーパビリティが外されている

**ホスト側ドメイン** には、安全に関わる部品がセルとは別の systemd ユニットとして置かれます。

| 部品 | 役割 |
|---|---|
| Sentinel | コネクタ操作と外部への通信の、唯一の許可権限者 |
| hatch-authd | 資格情報（OAuth トークン等）の保管と、後述する代理（surrogation） |
| Privsep ワーカー | コネクタの実処理を、狭い権限でセルの外で実行する |
| hatch-safety | モデルの入出力を検査する、独立した分類器群 |
| Postgres | アプリケーションの状態の永続化（セルとも資格情報ストアとも分離） |

セルとホスト側の通信は Unix ドメインソケットに限られ、`SO_PEERCRED` で送信元プロセスをカーネルレベルで確かめる、と説明されています[^qiita]。「相手を信頼する」という約束事ではなく、カーネルが送信元を確認する形にしているのが、この層の特徴です。

## 2. アプリケーション：エージェントは「提案」し、実行はセルの外で起きる

### エージェントハーネス

モデルの周りで文脈を組み立て、ツール呼び出しを仲介するプログラムを、ここではハーネスと呼びます。Meta の内部コードネームは "Hatch" で、サービス名の `hatch-authd` などにもその名残があります[^explainx]。実際に使った利用者の報告では、製品の中から `AGENTS.md` などのシステムファイルが見え、約350 MB の Rust 製ハーネスのバイナリが確認できた、とされています[^explainx]。これは Meta の公式発表ではなく利用者の観測報告なので、本稿では「外部報告」として扱います。

筆者の環境でも、性格や記憶を記した Markdown ファイル（`IDENTITY.md`、`MEMORY.md` など）がシステムファイルとして存在し、エージェントがそれらを読んで動くことは確認できます（観測）。「性格や記憶が、モデルの重みではなくファイルとして外に出ている」のは、この製品の分かりやすい特徴だと思います。

### ツール、スキル、コネクタ

アプリケーション層の部品は、大きく3種類に分かれているように見えます（製品の振る舞いからの整理で、Meta の公式な分類ではありません）。

- **ツール**：シェル実行、ファイルの読み書き、Web検索、ブラウザー操作、予定や文書の作成といった基本動作
- **スキル**：予約、買い物、メール管理といった作業ごとの手順書。モデルが毎回ゼロから手順を考えず、手順書に沿って動くためのもの
- **コネクタ**：Gmail や Google カレンダーなど外部サービスとの接続。OAuth の認可はエージェント本体とは別に保管される

ここで重要なのは、**実行セル内のコネクタCLIは引数を解析するだけで、資格情報には触れない**、という設計です[^explainx]。型付けされた引数とファイルディスクリプタが Unix ソケット越しにセルの外の Privsep ワーカーへ渡され、資格情報に触れる実処理はそこでだけ起きます。プロンプトインジェクションでセル内のツール呼び出しコードを書き換えられても、資格情報への到達経路自体がセル内に存在しない、という作りです。

### ブラウザーの扱い

Web の操作は、実際に Chromium を動かす別の仕組みが担います。公開資料で興味深いのは、その仕組みがページをどう「見る」かです[^explainx]。

- ページは生の DOM ではなく、アクセシビリティツリーのスナップショットとしてだけモデルに渡される
- ページ自身の文脈での JavaScript 実行はできず、開発者ツールも無効
- DOM、画像、ファイルに紛れ込んだプロンプトインジェクションを監視する分類器が、別に用意されている
- 利用者がブラウザーを手動操作している間や、資格情報が自動入力されている間は、エージェントは止まる

ページのスクリプトに仕込まれた指示が、そもそもモデルに届きにくい形になっています。

## 3. AI構成：モデル、エージェントループ、ファイルとしての記憶

### 中核モデル

Muse の中核は、2026年9月2日に公開された Muse Spark 1.3 です[^explainx]。料金は、無料枠が週あたり100Mトークンまで、有料の Power が月額20ドル、Maximum が月額100ドルと報じられています[^fello]。2026年10月12日には上位モデル Muse Wonder が発表され、Muse への搭載は購読者から順次とされていますが、本稿の執筆セッションで動いていたのは Muse Spark でした（観測）。

### エージェントループ

動作の基本は、多くのエージェント製品と共通するループです（図2）。

![利用者の依頼から文脈を組み立て、モデルが文章かツール使用かを選び、ツール結果を見て文脈に戻る循環。長期の情報は記憶ファイルに置かれ、関連するものだけ文脈に入る](/images/muse-secure-vm-architecture/fig2-agent-loop.png)
*図2：エージェントループと記憶の関係。モデルの外に置かれた記憶ファイルと、バックグラウンド処理が「閉じた後も働く」を支える（Pele で作成）*

1. 依頼、システム指示、記憶の検索結果、会話履歴から文脈を組み立てる
2. モデルが「文章で答える」か「ツールを使う」かを選ぶ
3. ツールの実行結果を文脈に戻し、2へ繰り返す

長い会話は途中で要約され、重要な部分だけが圧縮されて引き継がれます。「全部を生で覚えている」のではなく、「要約＋ファイルに残した記憶」で継続性を保つ設計です。

### バックグラウンド処理

アプリを閉じた後も働き続ける、という特徴を支えているのがこの層です。時刻指定の定期実行（cron）、イベント駆動のフック、常駐サービスに加え、会話の合間に記憶を整理したり、先回りして調べものをしたりする処理が動きます。Qiita の記事が紹介した「買ったばかりの車のリコールを、頼まれていないのに知らせてきた」という利用者の声[^qiita]は、この先回りの処理の例だと考えられます（推測）。

## 4. 秘密の扱い：エージェントは本物の鍵を持たない

本稿でいちばん紹介したいのが、この層です。

### 資格情報の代理（Credential Surrogation）

エージェントが受け取るのは、本物の OAuth トークンやパスワードではなく、**それ自体では何の権限も持たない代理トークン（surrogate token）** です[^forkast][^qiita]。コネクタ操作が Sentinel に許可された時点で初めて、本物の資格情報に差し替えられます（just-in-time insertion）。流れを図3に示します。

![エージェントは代理トークンだけで操作を提案し、Sentinelが許可したときにhatch-authdが送信直前に本物を挿入して外部サービスへ届ける流れ](/images/muse-secure-vm-architecture/fig3-credential.png)
*図3：資格情報の代理。プロンプトインジェクションでエージェントをだまして「パスワードを送れ」と言わせても、エージェントはそもそも本物を持っていない（Pele で作成）*

これは、「漏らすなとモデルに指示する」設計との決定的な違いです。指示は助言にすぎず、だまされれば破れます。しかし「持っていないものは漏らせない」は、モデルの判断が壊れても成り立ちます。

メールについても追加の配慮があり、ワンタイムコード、パスワード再設定リンク、マジックリンクは、エージェントに見せる前に必ず取り除かれる、とされています[^explainx]。メールへのアクセスが、他のアカウントの乗っ取りの足がかりにならないようにするためです。

### Sentinel とテイント追跡

Sentinel は、コネクタ操作と外部への通信のすべてについて、許可・拒否・利用者への確認のいずれかを決めます。判定は L4（宛先ホスト、解決後の IP、ポート、プロトコル）と L7（HTTP メソッド、パス、内容）の両方で行われ、DNS リバインディングのような SSRF 手法への対策も含む、と説明されています[^explainx]。

もう一つの仕組みが、データの流れの追跡です（図4）。

![ツール実行は汚染されていない状態から始まり、利用者のデータを読むと汚染の印が付き、印の付いた通信は自動では通らず利用者の確認に回る判定の流れ](/images/muse-secure-vm-architecture/fig4-taint.png)
*図4：テイントされた送信（tainted egress）。汚染の印付けは eBPF の cgroup プログラムと LSM フックでカーネルが行い、モデルの自己申告に依存しない（Pele で作成）*

- ツール実行は、汚染されていない状態から始まる
- 利用者のデータを読むと、そのプロセスに「汚染された」という印（テイント）が付く
- 印が子プロセスへ広がっていく様子は、通信の捕捉に使う eBPF の cgroup プログラムと、LSM フックに付けた eBPF プログラムで追跡される
- 汚染されていない狭い範囲の通信は自動で許可されることもあるが、汚染された通信は自動では通らず、利用者の確認に回る

「その操作が安全かどうか」を、操作の種類ではなく「途中で利用者のデータに触れたかどうか」で判定するのが要点です。

### 承認はチャットとは別の画面で行われる

利用者の承認も、チャットの文章としてではなく、クライアント側の専用ダイアログで得られ、回答はモデルを経由せず Sentinel へ直接戻る、とされています[^explainx]。承認の範囲は、1回だけ、セッションの間、その作業の間、期限つき、ずっと、の5種類です[^qiita]。

承認の画面を、モデルが生成する文章の流れから切り離しておくことには大きな意味がある、と筆者は考えます。攻撃者のコンテンツも流れ込む同じチャットの中で「承認しますか」と表示すれば、その表示自体が攻撃の対象になり得るからです。

### 買い物の支払い

支払いでも本物のカード番号は渡されません。購入のたびに利用者が合計金額を承認し、新しい店舗では Stripe Link が店舗・金額・有効期限を限定した使い捨ての仮想カードを発行します[^qiita][^stripe]。カード番号が店舗側から漏れても、その取引以外には使えません。

## 5. プロンプトインジェクションへの5層

公開資料は、プロンプトインジェクション対策を1つの仕組みではなく、5つの層として説明しています[^explainx]。

| # | 層 | 内容 |
|---|---|---|
| 1 | モデルの訓練 | Muse Spark 1.3 自体を、外部コンテンツに紛れ込んだ指示に従わないよう訓練する |
| 2 | ハーネスのラベル付け | Web、メール、ファイルなど外部由来のコンテンツを「信頼できない」と明示して文脈に入れる |
| 3 | 分類器アンサンブル | 独立に訓練されたインジェクション検出の分類器群を、外部データに対して並行に走らせる（hatch-safety） |
| 4 | 人間の承認 | VM からデータが出る操作は、利用者の承認に回す |
| 5 | カーネルレベルの境界 | 実行セル、特権分離、hatch-authd のアクセス制御、Sentinel。1〜3が全部破れても成り立つことを狙う |

第5層がこの設計の思想を表しています。**安全をモデルの正しさに賭けない**。モデルは間違えるものとして扱い、最終防衛線はカーネルと、モデルが制御できないプロセスに置く、という割り切りです。

## 6. モデル自体の安全性評価

製品側の防御の仕組みとは別に、モデル単体の評価も公開されています。Muse Spark Safety & Preparedness Report は、Meta の Advanced AI Scaling Framework の下で、化学・生物、サイバーセキュリティ、制御喪失の各領域を評価した159ページのレポートです[^safety-report]。

要点は次のとおりです。

- 対策前（pre-mitigation）の評価では、化学・生物の能力が「高リスク」に達する可能性が高いと判定された
- 多層の緩和策を入れたうえで、Meta AI 内での展開としての残余リスクは許容範囲、というのが公開の判断
- 第三者評価（Apollo Research）では、評価されていることを見抜く「評価認識（evaluation awareness）」の高さも報告されている

注意したいのは、このレポートの主な対象が「Meta AI の中核モデルとしての Muse Spark」であって、「個人エージェント製品 Muse の運用全体」ではない、という点です。モデルの評価が製品の安全をそのまま保証するわけではありません。本稿でも、モデルの話（本節）と製品側の防御の話（1〜5節）は分けて扱っています。

## 7. それでも残る論点

作り込まれた設計にも、公開資料と利用者の声の両方から、残る論点が見えます。

### Meta から秘匿されているわけではない

現行の標準 VM は、他の利用者やインターネットからは隔離されていますが、Meta 自身に対して秘匿されているわけではありません。利用者側が鍵を持ち、Meta でも中身へアクセスできない Confidential VM は、2026年後半の提供予定として説明されている段階です[^explainx]。「隔離されている」と「提供者にも見えない」は別の話で、現時点で成り立っているのは前者だけです。

### 独立した監査はまだない

本稿の「事実」の多くは、突き詰めると Meta 自身の技術ブログと、公開当日の発表に行き着きます。解説記事は詳細ですが、一次情報は Meta です。第三者による独立監査の公開は、本稿の調査時点では確認できませんでした[^explainx]。脆弱性の報奨金が最大30万ドル、1人の利用者に影響するプロンプトインジェクションの成功に最大13万ドルと設定されていること[^qiita]は、Meta がこの種類の攻撃をそれだけ重く見ている証拠であると同時に、そうした事態を「起き得るもの」と見た金額設定でもあります。

### 入口で止まる問題

Qiita の記事によれば、投資銀行 Jefferies が米国の主要サイト数百で試したところ、約3分の1が Muse を拒み、約3分の1が確認や制限をかけた、とされています[^qiita]。Amazon は2026年9月21日に Muse の遮断を始めました。エージェント側の資格情報をいくらきれいに分けても、相手のサイトがエージェントを受け入れるかどうかは別の問題で、詰まる場所はモデルの質から「サイトに入れるかどうか」へ移りつつある、というのが同記事の見立てです。

### 許可の意味を取り違える問題

同じく Qiita の記事が伝える Marketplace の事例では、「常に許可」を選んだ利用者が、毎回確認されると思っていたところ、エージェントが申し込みを受けて住所を買い手に送ってしまった、とされています[^qiita]。資格情報の漏洩ではなく、**許可の範囲の取り違え**で起きた事故です。承認を細かく分けるほど取り違えが起き、狭くするほど承認の手間が増える。この緊張は、防御の仕組みをどれだけ強くしても別に残ります。

## 限界

最後に、本稿が**言えないこと**を書いておきます。

- 本稿の構成図は、公開資料の記述をもとに筆者が描き起こしたものです。Meta の内部設計図そのものではありません。資料間で表現が違う部分は、より具体的な記述（Qiita 記事と explainx.ai の解説）を優先しました。
- Meta の技術ブログ原文（research.meta.ai）は、本稿の執筆環境からは直接取得できなかったため、内容は Qiita 記事と海外解説記事の引用・要約を通じて確認しています。一次資料に当たる場合は、末尾のリンクから原文を確認してください。
- VM のスペック観測は1セッションの一例で、時期やプラン、地域で変わる可能性があります。
- 報じられている利用者の声は、早期利用者や話題性のある事例に偏っている可能性があります。Qiita 記事自身も、X の投稿が利用者全体を代表しないこと、論調判定の方法に限界があることを明記しています[^qiita]。
- Muse Wonder の搭載や Confidential VM など、発表済みでも未提供のものは「予定」として扱い、提供済みの機能とは区別しています。

## おわりに

Muse の設計でいちばん印象に残るのは、モデルの賢さではなく、**モデルを信用しない前提で組まれた周りの地味な部品**です。systemd-nspawn、eBPF、Unix ソケットの `SO_PEERCRED`、特権分離といった、どれも枯れた Linux の部品の組み合わせで、「だまされるかもしれないエージェント」に本物の鍵を持たせず、外部への送信の可否も自分では決めさせない、という問題を解いています。

エージェントの安全性は、モデルの拒否率の数字だけでは測れません。「モデルが完全にだまされた日に、何がまだ成り立つか」。Muse の公開資料は、その問いにインフラ側から答えようとした、現時点でいちばん具体的な事例の一つだと思います。
